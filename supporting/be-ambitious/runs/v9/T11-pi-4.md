```text
Make our marketing website load faster. The home page takes about 10 seconds to load on mobile.

Assumption: success means mobile visitors can see the main marketing message and use the primary call to action sooner, without losing content, functionality, accessibility, or measurement that the business relies on.

Measure before changing anything. Treat “about 10 seconds” as a reported observation, not a verified baseline or an LCP measurement. Establish a reproducible mobile profile with a named viewport, CPU and network throttling, cache state, and build. Run 10 cold-cache baseline navigations; repeat under identical conditions after changes. Record navigation load-event time, Largest Contentful Paint (LCP), and when the primary call to action becomes visible and operable. Fix the content and interaction checks before comparing builds.

Use Chrome DevTools Performance traces and network waterfalls to identify what delays useful content: request dependencies, server response time, image delivery, render-blocking resources, fonts, JavaScript execution, and third-party work. Inspect the actual responses, assets, and source responsible rather than optimizing a Lighthouse score in isolation. Use Lighthouse as a diagnostic, not as proof of the reported 10-second delay.

Optimize the measured critical path first. Verify each substantive change against the baseline so unrelated improvements do not mask a regression. Aim for median cold-cache mobile LCP below 1.5 seconds using the measured bottlenecks to choose between image optimization, resource prioritization, render-blocking work reduction, JavaScript reduction, and caching changes. If one approach stalls, try the next supported approach within the authorized scope and available time. Keep measurable improvement over the verified baseline as the acceptance bar; report the stretch target separately as met, missed, or unverified.

Borrow fault-injection testing from reliability engineering: stall nonessential third-party requests in a controlled browser test to discover whether analytics, embeds, or other external dependencies prevent the main message and primary call to action from becoming usable. Fix demonstrated loading dependencies without silently removing business functionality.

Preserve the site's marketing content, visual intent, navigation, forms, accessibility, and existing analytics behavior. Do not submit real leads during testing. Use existing authorized development and test environments; do not deploy to production, buy services, add tracking, or change infrastructure without authorization. Summarize the changes, comparable before/after measurements, remaining bottlenecks, and any unverified claims.

First check: identify the target website URL, relevant source and build instructions, authorized development environment, existing test commands, and available browser-profiling capabilities. Confirm the primary call to action and how to test it without sending real submissions. Confirm whether the reported mobile conditions are known; otherwise label the chosen test profile as a proxy. If a dependency is missing, continue only with supported, authorized work and leave affected results unverified.

Judge: a repeatable browser benchmark compares 10 baseline and 10 changed-build cold-cache navigations under the same recorded mobile profile, reporting medians and run-to-run spread for load-event time, LCP, and primary-call-to-action readiness; pass only if the evidence supports a reproducible reduction in load-event time without a regression in LCP or call-to-action readiness beyond measured variability, existing applicable tests pass, and browser checks preserve the main message, navigation, primary interaction, and analytics behavior; the third-party-stall test must not block the main message or primary interaction; report the median-LCP stretch below 1.5 seconds separately, and leave conclusions unverified wherever missing evidence or measurement noise prevents judgment.
```

- `altitude`: From a faster-loading page to earlier access to the marketing message and primary action; adds readiness measurements while preserving the site's purpose. No production rollout or new tracking.
- `depth`: Replaces the approximate 10-second observation with controlled baseline measurements, raw traces, bottleneck-led changes, and a separate sub-1.5-second LCP stretch. Costs local profiling and repeated test runs; does not treat the stretch as the owner's acceptance bar.
- `range`: Reliability engineering contributes third-party fault injection, exposing external dependencies that can make an otherwise optimized page unusable. Runs in a controlled browser without real submissions.
- Skipped lenses: none; each contributes a distinct outcome, diagnostic method, or failure test.
- Owner actions: identify the website and authorize source/test access; confirm the primary interaction and known mobile conditions. Deployment, purchases, new tracking, and infrastructure changes remain outside authorization.
