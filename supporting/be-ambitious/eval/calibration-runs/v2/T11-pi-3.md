### Rewritten prompt

```text
Make our marketing website load faster, prioritizing the home page on mobile, which reportedly takes about 10 seconds to load.

Intended result: visitors can see and use the home page sooner, and the site owner receives a measured before/after comparison.
Assumption: the business goal is to reduce waiting without weakening the marketing message, accessibility, analytics, or primary conversion paths. Do not claim conversion improvements without evidence.

First verify the website URL, relevant repository, available test tools, and permission to run tests. Identify the current build and the mobile device/network conditions behind the 10-second report. If those conditions are unknown, document a reproducible mobile test profile and label the reported time as unverified. Do not assume access to production analytics, hosting, or paid services.

1. Establish what visitors are waiting for.
   Before editing, measure the current home page using Lighthouse or WebPageTest and browser performance traces, depending on available tools. Record the build, device/network profile, cache state, and test location.
   Run at least five comparable cold-cache tests. Report median and variability for Largest Contentful Paint (LCP), first paint, load-event time, and layout shift. Identify which measurement best captures the reported wait, and select the primary comparison metric before making changes.
   Inspect raw network waterfalls, main-thread traces, resource sizes, and server-response timing rather than relying on a performance score.

2. Fix the dominant causes, not the easiest warnings.
   Determine whether the delay comes from server response, render-blocking resources, hero-image discovery or size, fonts, JavaScript execution, third-party scripts, or another measured bottleneck.
   Use critical-path analysis to identify which dependencies actually delay visible, usable content. Use bundle analysis if JavaScript is implicated; inspect image dimensions, formats, loading priority, and compression if imagery is implicated.
   Implement the smallest effective changes within the existing site's approved scope. Do not remove meaningful content, tracking, consent controls, or functionality simply to improve a score.

3. Pursue a stronger result.
   Aim for mobile LCP of 2.5 seconds or less using critical-path reduction and evidence-led resource optimization under the documented test conditions. This is a stretch target, not a claim about real-user performance.
   If the first approach stalls, inspect the next measured bottleneck and try another supported approach before reporting a miss. Stay within any existing budget and deadline; ask before expanding scope.

4. Protect what makes the page useful.
   Borrow controlled-experiment methods: compare equivalent builds under the same conditions, and use isolated changes where practical to test causal explanations.
   Borrow user-journey testing: check the primary call to action, navigation, forms, consent behavior, accessibility, and representative mobile layouts. Red-team the apparent improvement: did work merely move until after the measurement, introduce layout shifts, or make the page appear ready before it responds?
   Report actual measurements, changed files, trade-offs, remaining bottlenecks, and any missed target.

Approval gates: obtain owner approval before paid services, new access, production deployment, infrastructure changes, new telemetry, collection of visitor data, or work beyond the home-page performance scope. If existing, authorized real-user data is available, use it to corroborate laboratory findings; otherwise leave real-world impact unverified.

Judge and pass condition: rerun the same before/after mobile test protocol. Pass when the preselected primary wait metric improves beyond observed run-to-run variability, critical journey checks pass, and other measured usability metrics show no material regression. Report all measured results, including whether the 2.5-second LCP stretch was reached. Missing baseline evidence or an unrun judge leaves the improvement unverified.
```
