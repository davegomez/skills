### Rewritten prompt

```text
Make our marketing website load faster. The home page reportedly takes about 10 seconds to load on mobile; treat that figure as unverified until measured.

Outcome: help mobile visitors see and use the home page sooner, not merely improve a performance score. Give the website owner evidence to decide whether the changes are ready to ship.

Assumptions to validate: the home page is the initial scope; its marketing message, primary calls to action, accessibility, and required analytics should remain intact. No technology stack, performance tooling, production access, budget, or deadline has been confirmed.

1. Verify the setup and establish the baseline.
- Check available repository, build/run instructions, homepage URL, test tools, and any existing mobile performance data. Identify missing dependencies. Do not obtain new access or incur costs without approval.
- Clarify what “10 seconds to load” describes: first useful content, largest contentful paint (LCP), page-load completion, or time until the main action works. If clarification is unavailable, measure these separately.
- Use a representative mobile viewport, device/network profile, and consistent test conditions. Record the page/build, environment, throttling, cache state, and test settings.
- Run at least five comparable baseline tests. Report median and spread, not just the best run. If field data is already available, inspect mobile experience separately; do not present lab results as real-user percentiles.

2. Diagnose from raw evidence before choosing fixes.
- Inspect network waterfalls, browser performance traces, resource sizes, JavaScript execution, rendering, and server response timing using available tools such as browser DevTools, Lighthouse, and the project’s bundle analyzer.
- Identify the critical rendering path: what actually delays the meaningful hero content and primary call to action?
- Test the premise that downloaded assets or frontend code are the main cause. Distinguish server delay, network transfer, third-party work, and main-thread blocking. Rank changes by measured contribution, likely benefit, and implementation risk.

3. Make targeted improvements within the approved scope.
- Use the evidence to choose interventions—for example, image sizing and formats, LCP-resource discovery, font loading, removal of unused code, deferred nonessential work, or caching. Do not apply these as a generic checklist.
- Apply perceptual-performance methods from UX: prioritize meaningful content and usable controls rather than hiding unfinished work behind a loader or manipulating the score.
- Use controlled before/after experiments from causal inference: keep test conditions fixed and isolate major changes where practical so improvements can be attributed.
- Aim for mobile lab LCP of 2.5 seconds or less under the agreed representative conditions, using critical-path analysis and targeted changes. This is a stretch target, not a replacement for the original requirement to make the page faster. If one approach stalls, investigate the next evidenced bottleneck before reporting a miss, within any confirmed budget and deadline.
- Preserve existing functionality. Red-team the result for misleading wins: missing content, broken calls to action, delayed interaction, layout shifts, disabled required tracking, or gains that occur only with a warm cache.
- Changes outside the home page, infrastructure or paid-service changes, new access, deployment, removal of third-party functionality, and substantial content/design changes require owner approval. Recommend them with evidence if needed; do not perform them without approval.

4. Deliver the implementation and an evidence-backed summary.
- Identify changed file paths, the bottlenecks addressed, and the reasoning behind each change.
- Report measured baseline and final results, test conditions, variability, functional checks, remaining bottlenecks, and whether the stretch target was reached.
- Separate observed findings from hypotheses. Do not claim improved conversion or production performance without the corresponding evidence.

Judge and pass condition:
Use the same repeatable browser-performance test before and after, with at least five runs per version under matched representative mobile conditions. Pass the original task when the primary user-visible loading measure improves beyond baseline run-to-run variability, page-load timing is also reported, and homepage content, primary actions, and existing functional checks still pass without material interaction or layout-stability regressions. Report the measured improvement even if the 2.5-second LCP stretch target is missed. If representative testing or required functional checks cannot run, mark the corresponding outcome unverified rather than declaring success.
```
