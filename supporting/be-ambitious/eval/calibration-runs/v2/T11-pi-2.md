### Rewritten prompt

```text
Make our marketing website load faster, prioritizing the home page, which reportedly takes about 10 seconds to load on mobile. Treat that timing as an unverified report until measured.

Intended result: a demonstrably faster mobile experience for visitors, with reproducible evidence the site owner can use to approve the changes.
Assumption: visitors need to see useful content and use the primary navigation and call to action sooner—not merely trigger the browser’s load event sooner.

First establish what is available:
- Check repository access, build/run instructions, the home-page URL, existing tests, and available performance tools.
- Check whether authorized real-user monitoring, analytics, and a representative mobile device/network profile exist. Do not assume access or install third-party tracking.
- Record missing dependencies. Continue with available local or staging evidence, but label production and real-user conclusions unverified until their judges run.

Establish a baseline before editing:
- Clarify whether “10 seconds” means first useful content, largest content appearing, page load, or usable interactions. If clarification is unavailable, measure these separately and use Largest Contentful Paint (LCP) as the provisional primary loading metric.
- Record the commit/build, route, device or emulation, network/CPU settings, and cache state. Run at least five comparable mobile trials; report median and spread. Check a repeat visit separately so caching cannot hide a slow first visit.
- Use Chrome DevTools Performance/Network traces and Lighthouse, or available equivalents, to inspect raw request timing, resource sizes, render blocking, main-thread work, layout shifts, and the LCP element. Use existing field data when authorized; distinguish field measurements from lab results.

Find and fix the actual critical path:
- Test competing explanations—server latency, oversized media, blocking fonts/styles, JavaScript execution, or third-party work—rather than assuming the largest file is the bottleneck.
- Use critical-path analysis to identify dependencies delaying useful content. Use controlled before/after experiments, changing one suspected bottleneck at a time where practical, to establish which changes help.
- Implement the highest-impact supported fixes with the smallest maintainable changes. Preserve content, branding, responsive layouts, accessibility, navigation, and primary calls to action.
- Aim for mobile LCP ≤2.5 seconds using the measured bottlenecks. If one approach stalls, test the next evidence-supported approach within the available budget and deadline. Report the achieved result even if this stretch target is missed.
- Do not game the metric by hiding important content, replacing useful content with placeholders, or moving blocking work into the visitor’s first interaction. Check early scrolling and primary-CTA interaction as adversarial cases.

Stay within website performance work. Obtain owner approval before paid services, new access, production deployment, infrastructure migration, removing business functionality or tracking, or expanding into unrelated pages or systems.

Deliver the implementation, a concise explanation of root causes and changes, reproducible measurement commands/configuration, before/after results, and remaining limitations. Add an appropriate performance regression check using existing tooling where feasible. Do not claim improved conversions or production performance from lab measurements alone.

Judge and observable pass condition: rerun the same mobile measurement protocol against baseline and changed builds. Pass when the primary loading metric improves reproducibly beyond observed run-to-run variation, existing relevant tests pass, and mobile visual and interaction checks show no material regression. Report absolute and percentage changes, trial spread, LCP, layout stability, and interaction evidence; do not substitute a Lighthouse score for timings. The ≤2.5-second LCP goal is a stretch target, not a replacement for the requested improvement. Production or field-performance claims remain unverified until authorized field measurements confirm them.
```

### Ledger

- `altitude` — **Fit:** moves “make the website load faster” toward visitors seeing and using the mobile home page sooner. Matched baseline/changed-build trials judge the improvement; production validation requires confirmed access and deployment approval.
- `depth` — **Fit:** raw traces, request waterfalls, repeatable trials, and critical-path analysis replace guesswork. Tests the presumed cause before fixing it; adds a 2.5-second LCP stretch target without making it the original requirement.
- `range` — **Fit:** experimental design isolates causal improvements; human–computer interaction checks whether earlier rendering produces usable content; adversarial interaction tests expose work merely deferred beyond the loading metric. Adds validation effort, not new business scope.
- **Skipped lenses:** none; each improves the outcome, method, or judge.
- **Unresolved owner actions:** confirm available access and any budget/deadline constraints; clarify the reported “10 seconds” if possible. Approve any paid tooling, new permissions, production deployment, infrastructure changes, functionality/tracking removal, or broader scope before execution.
