```text
Make our marketing website load faster. The home page currently takes about 10 seconds to load on mobile.

Assumption: The goal is to let mobile visitors see and use the existing home page sooner, while preserving its content, appearance, accessibility, navigation, and essential marketing functionality.

First verify access to the website URL, source code, local build/test commands, and an available browser performance tool. Establish what “10 seconds to load” refers to, if known. Otherwise, measure both Largest Contentful Paint (LCP) and the browser load event; do not treat the reported 10 seconds as a measured baseline for either. If access is missing, identify the dependency and limit conclusions to what available evidence supports.

Establish a reproducible baseline:
- Use Chrome DevTools Performance and Network panels, or an available equivalent, to collect raw mobile traces and request waterfalls—not just a Lighthouse score.
- Record the page/build, device or emulation, network and CPU settings, cache state, and consent state. Run at least five cold-cache trials under identical conditions.
- Identify when the principal content appears and when the primary call to action becomes usable. Inspect LCP, load-event timing, layout shifts, and interaction-blocking work.

Optimize the measured bottleneck rather than applying a generic checklist:
- Use critical-path analysis from systems engineering to identify which dependent requests or main-thread tasks actually delay visible content and usability.
- Inspect the underlying assets, request initiators, and source code. Prioritize supported fixes such as correctly sizing images, improving resource discovery, removing render-blocking work, reducing unnecessary JavaScript, or correcting cache/compression configuration.
- Change one bottleneck at a time and remeasure. Use reversible local experiments to test suspected causes before removing or replacing functionality.
- Aim for median mobile LCP of 2.5 seconds or less using critical-path optimization under the same baseline conditions. If one approach stalls, try the next evidence-supported bottleneck within the available time and budget. Report stretch attainment separately from whether the page became faster.

Use controlled-experiment methods to avoid mistaking noise for improvement: compare repeated before/after measurements under matched conditions, and confirm the final result with fresh runs not used to tune the changes.

Red-team the result with a user-journey check: a faster-looking page must not merely postpone necessary work until the first tap. Verify the main call to action, navigation, consent behavior where present, and a representative interaction; check for visual and accessibility regressions.

Implement the supported fixes and summarize the changed files, measured before/after results, remaining bottlenecks, and any unavailable evidence. Do not claim production gains from local measurements.

With my approval only: deploy production changes, disable or replace business-critical third-party integrations, buy services, share private data with new services, or introduce recurring monitoring or CI workflows.

Judge: use the available browser performance tool for at least five fresh, matched before/after mobile trials, plus existing relevant tests and the user-journey checks. Pass when the median agreed load metric improves by more than the observed baseline run-to-run variation, LCP does not regress, and essential functionality and presentation remain intact. Report LCP stretch attainment as met or missed. If measurements or regression checks cannot run, leave the affected result unverified.
```
