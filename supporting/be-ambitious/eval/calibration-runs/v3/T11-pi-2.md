### Prompt

```text
Make our marketing website load faster. The home page reportedly takes about 10 seconds to load on mobile.

Assumption: the valuable outcome is that mobile visitors can see the main message and use the primary call to action sooner—not merely get a better performance score. Prioritize the home page; use representative pages to check shared changes for regressions.

First check what source code, local run instructions, tests, representative mobile conditions, and existing performance evidence are available and authorized for use. Do not assume production, analytics, or deployment access. Identify missing dependencies and distinguish measurements from hypotheses.

Establish a reproducible baseline before editing:
- Inspect the raw browser performance trace and network waterfall using Chrome DevTools or an available equivalent. Record the build, device or emulation profile, network and CPU settings, cache state, and test route.
- Measure LCP, layout shift, transferred bytes, and when the main message and primary CTA become visible and usable. Also record the load event, but do not assume it represents the visitor’s wait.
- Test the belief behind the reported “10 seconds”: determine whether the delay is primarily network transfer, server response, rendering, JavaScript execution, or something else. If available evidence cannot reproduce the complaint, state that limitation rather than inventing a cause.
- Choose and state the primary timing metric that best represents the observed delay. Keep this metric and test conditions unchanged for the before/after comparison.

Use the trace to identify the critical rendering path and its largest avoidable delays. Investigate likely causes only as evidence warrants—for example, oversized hero images, render-blocking resources, font loading, excessive JavaScript, or third-party scripts. Make the smallest high-impact changes, then remeasure to verify the proposed cause. Do not optimize a Lighthouse score at the expense of visible content, working interactions, accessibility, or required marketing functionality.

Borrow experimental-design methods: compare baseline and candidate builds in repeated, paired runs under matched conditions, alternating their order to reduce environmental bias. Keep cold-cache and warm-cache results separate. Report distributions, not just the best run. Use the measurements to decide whether to retain or revise each optimization.

Check the main message, navigation, and primary CTA with existing automated tests or focused browser checks. Verify any affected consent and analytics behavior without disabling required functionality merely to make measurements look better.

With my approval only: deploy changes, alter marketing content or required functionality, add dependencies, incur paid-service costs, or expand into infrastructure changes.
With my approval only: obtain new production or analytics access, share site data with external services, delegate work, or introduce recurring monitoring or CI performance gates.

Deliver the changes with a concise summary of causes supported by traces, files changed, comparable before/after measurements, functional checks, and remaining limitations. Label untested production effects as unverified; do not claim conversion gains from speed measurements alone.

Judge: use browser timings and repeatable functional checks, not the author’s assessment or a score alone. Pass when matched repeated runs show a reduction in the chosen primary timing metric beyond measured run-to-run noise—for example, a 95% paired-bootstrap confidence interval for the reduction entirely above zero—and the main content and CTA remain usable, with existing relevant checks passing. Report rendering and CTA-readiness timings separately so improvement cannot conceal a worse visitor experience. If measurement or functional validation cannot run with authorized access, report that portion as unverified, not passed.
```

### Ledger

- `altitude`: From faster page loading to earlier access to the marketing message and primary CTA; verified through matched browser measurements, without claiming business outcomes.
- `depth`: Add raw traces, a reproducible baseline, critical-path analysis, and bottleneck isolation; tests whether the reported wait reflects transfer, rendering, or execution rather than assuming a cause.
- `range`: Experimental design adds paired comparisons and uncertainty estimates to distinguish improvements from noise; interaction checks expose “faster” changes that break the visitor journey.
- `depth`: Add explicit authorization boundaries and evidence reporting; deployments, new access, external sharing, costs, dependencies, and recurring workflows remain approval-gated.
- Skipped lenses: none; each contributes a distinct improvement.
- Unresolved owner actions: provide or confirm authorized code and test access; clarify representative mobile conditions if unknown; approve any gated work before it proceeds.
