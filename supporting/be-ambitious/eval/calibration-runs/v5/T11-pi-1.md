### Rewritten prompt

```text
Make our marketing website load faster, focusing on the home page on mobile, which currently takes about 10 seconds to load.

Assumption: the goal is for mobile visitors to see the core message and use the primary call to action sooner, without breaking the page, its accessibility, or existing marketing functionality.

First verify the available, already-authorized repository, local or preview environment, and measurement tools. Use Chrome DevTools Performance and Network panels and Lighthouse, or available equivalents. Identify missing dependencies before relying on them; do not request new access or incur costs without approval.

Establish a reproducible baseline:
- Record the URL/build, device or emulation profile, network and CPU settings, and cache state.
- Run five comparable cold-cache mobile measurements. Record median Largest Contentful Paint (LCP) and the navigation load-event time separately. Treat “about 10 seconds” as a reported symptom, not a measured baseline or an LCP measurement.
- Capture screenshots and test the primary call to action to establish what “usable” means for this page.

Diagnose from raw network waterfalls and performance traces, not just an aggregate performance score. Identify the actual critical path: server response, render-blocking resources, the main visual asset, fonts, JavaScript execution, or third-party work. Rank fixes by measured contribution to delay, expected benefit, and implementation risk.

Aim for median mobile LCP of 2.5 seconds or less using critical-path optimization under the same baseline conditions. Test the most promising cause first; if it stalls, try the next evidence-supported approach within the existing scope, budget, and deadline. Preserve the page’s content, branding, accessibility, and intended functionality. Do not improve the score by hiding important content or removing required functionality.

Use experimental design: isolate major changes and compare traces before and after so improvements can be attributed to actual changes rather than run-to-run variation. Prioritize visitor-visible improvement over a higher synthetic score.

Use an adversarial usability check: on a slow mobile connection, try to read the main message and activate the primary call to action before the page finishes loading. Check that deferred scripts, fonts, or images do not leave controls broken, obscure content, or cause disruptive layout shifts. Do not claim increased conversions without conversion evidence.

Deliver the focused code changes, applicable tests, and a concise before/after report with measurement settings, results, remaining bottlenecks, and any unverified claims. Report the 2.5-second stretch target separately as met, missed, or unverified.

With my approval only: deploy to production, change shared infrastructure, purchase services, or obtain new access or share data with external services.

Judge: rerun the same five-run mobile measurement protocol against the changed build and run the relevant regression checks. Pass when median LCP improves beyond baseline run-to-run variation, navigation load-event time does not materially regress, and the main message and primary call to action remain usable with no detected functional or accessibility regressions. Include the individual timings as evidence. Missing measurements leave performance improvement unverified.
```
