### Rewritten prompt

```text
Make our marketing website load faster, focusing on the home page on mobile. The reported load time is about 10 seconds; treat that as an observation to reproduce, not a verified baseline or a specific performance metric.

Assumption: the useful outcome is that mobile visitors can see the main message and use the primary call to action sooner—not merely obtain a better benchmark score.

First check access to the website, source repository, local build instructions, and available browser-performance tools. Use only authorized access. Identify missing dependencies and proceed only with work the available evidence supports. Do not send private URLs, code, or visitor data to external testing services without approval.

Reproduce the slow experience before changing code:
- Use Chrome DevTools Performance and Network traces, or available equivalents, to inspect the critical rendering path, resource waterfall, main-thread work, and when the main content and primary call to action become usable.
- Establish a repeatable mobile test profile: same build mode, device or emulation, network and CPU settings, cache state, and page content.
- Record at least five baseline runs. Measure LCP and identify which observable timing actually captures the reported delay. Choose and document that primary timing before optimization; do not silently equate “load” with LCP.

Use the raw traces and source code to find the dominant bottleneck rather than applying a generic checklist. Prioritize improvements by their contribution to the measured critical path. Depending on the evidence, investigate image delivery, render-blocking resources, font loading, JavaScript execution, and request dependencies.

Aim for a 75% reduction in the measured primary mobile loading time using trace-guided critical-path optimization. If one approach stalls, try the next evidence-supported approach within the existing budget and deadline. This is a stretch target, not a claim that the reported 10 seconds has been verified.

Borrow controlled-experiment methods: test major changes separately under the same conditions, and use local-only resource blocking or feature ablation to check whether a suspected bottleneck actually causes the delay. Confirm the combined result on fresh runs not used to choose the changes.

Preserve the page’s content, branding, accessibility, consent behavior, analytics, and primary conversion flow. Do not make the page appear faster by hiding required content, delaying essential interactions, or moving expensive work just beyond the measurement window.

Implement the supported improvements and report changed file paths, before/after measurements, test conditions, functional checks, and remaining bottlenecks. Report the stretch target as met, missed, or unverified, separately from whether the site became measurably faster.

With my approval only: deploy to production or change hosting/CDN configuration.

Judge: repeat the matched mobile tests on the baseline and final builds, with at least five fresh runs each, and run available functional checks. Pass when the primary loading-time reduction is repeatable beyond baseline run-to-run variation, the main message and call to action become usable sooner, and required behavior is preserved. Report medians and ranges, not just a Lighthouse score. Missing reproducible timing or functional evidence leaves the affected result unverified.
```

### Ledger
