## Raw Android bytes and the conversion rule

All 20 original Android JPEG files are retained in
[`android/captures-2026-09-08/`](android/captures-2026-09-08/). The 5 redacted Android files
(S-A05, S-A14, S-A16, S-A17, S-A18) were replaced by their redacted versions on 2026-09-09; the other 15
are unchanged. Each retained file is named
`<screenshot id>-<original file name>`, for example
`S-A17-90964e9c-1519-44e9-bf03-8a0bcb19f18a.JPEG`. The copies match the SHA256 values in the table
above.

The runtime asset tree accepts PNG files only. A batch that imports an Android capture decodes the
JPEG losslessly to PNG and writes the PNG under
`skills/native-ui-patterns/assets/android/settings/`. The decode step does not re-encode the JPEG
and does not change the pixel values. The PNG is a new file with new bytes, so the runtime SHA256
in `screenshot-map.tsv` differs from the JPEG SHA256 in the table above. The JPEG remains the
original evidence of record.

## Manual redaction (2026-09-09)

The device owner redacted personal data by hand, in the original location, before any further
import. 25 files changed: 20 iOS PNG and 5 Android JPEG. The method is a solid black rounded box
over each covered text value, plus a blur over one face photograph in S-I04. The boxes cover
values only; row labels, controls, dividers, and chevrons remain. The table in
[Image record](#image-record) above records the files as they exist now, after this redaction.
The pre-redaction bytes are not stored in the repository. At the owner's request, the same black-box treatment was applied by script on 2026-09-09 to nearby network names on S-I14, S-I15, S-A14, and S-A16; the boxes keep the row layout and the color profile. Later on 2026-09-09 the owner boxed the account identifier in the footer of S-I28 on the runtime copy only (`sign-out-row-footer.png`); the owner's capture folder, deleted later that day, held the pre-box bytes, so the S-I28 row above records the runtime copy.
